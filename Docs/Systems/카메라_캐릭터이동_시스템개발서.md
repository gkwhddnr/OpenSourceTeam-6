## 1. 개발 결과물과 경계

첫 결과물은 독립 실행 가능한 개인 검증 씬과 공용 통합 씬, 플레이어 프리팹,
직원 프리팹, 소스 편집 가능한 카메라·이동 라이브러리다.
음성 입력·직원 성격·감정·FSM·스토리는 별도 담당 기능이며 이동 내부에 넣지 않는다.
직원은 목적지 이동 결과만 알려주고 다음 업무는 외부 행동 시스템이 결정한다.

직원 외 일반 NPC의 이동도 확장 설계에 포함한다. 직원은 업무 지시를 받는 캐릭터,
일반 NPC는 손님·방문자·주변 인물 등 별도 행동 규칙으로 움직이는 캐릭터로 구분한다.
일반 NPC는 첫 시제품 구현·완료 기준에는 포함하지 않고, 도입 결정 후 별도 Issue로 개발한다.

| 자체 코드가 담당 | Unity 기능을 활용 |
|---|---|
| 수평 이동 의도 계산, 입력 크기 제한 | Input System의 키보드·마우스 입력 |
| yaw/pitch 계산과 제한 | Camera·Transform의 장면 반영 |
| 요청 식별자·상태 전이·취소·시간 제한 | CharacterController의 충돌 이동 |
| 잠금 토큰·읽기 전용 결과·검증 | NavMeshAgent의 경로 탐색·이동 및 NavMeshSurface 베이크 |

Unity를 대체하거나 새 물리 엔진을 만들지 않는다. 엔진과 분리할 가치가 있는 규칙은
Core에 두고, Unity API는 Unity 계층 안에서 사용한다. 구체적인 성능 우위는 측정 전 주장하지 않는다.

### 초기 구현 선택과 이유

- 플레이어: CharacterController 기반. 평탄한 매장의 직접 보행과 즉시 정지 요구에 맞춘다.
  Rigidbody 방식은 힘·관성이 핵심일 때 다시 비교한다. 첫 범위에서는 혼용하지 않는다.
- 직원: NavMeshAgent 기반. 경로 탐색을 새로 구현하는 대신 요청·실패 계약에 집중한다.
- 카메라: 직접 작성한 보기 규칙 + Camera 연결부. 첫 범위에서는 Cinemachine을 추가하지 않는다.
- 입력: 설치된 Input System을 사용한다. 기존 공유 입력 에셋을 변경하기보다
  담당자 소유 입력 에셋을 만들고 공용 적용 시 중복 활성화 여부를 확인한다.

## 2. 전체 구조와 참조 방향

```text
키보드·마우스
  → PlayerInputReader → PlayerRigController
      ├→ LookSolver (Camera.Core) → yaw/pitch
      ├→ MovementSolver (Movement.Core) → 이동 의도
      ├→ CharacterControllerMotor → 실제 위치·충돌 결과
      └→ FirstPersonCameraPresenter → 눈 위치·회전 적용

외부 행동 시스템
  → IAgentMovement 요청
  → EmployeeMovementController
      ├→ MoveRequestTracker (Movement.Core)
      └→ NavMeshAgentDriver → 경로·실제 이동
  → 읽기 전용 상태 / 요청 종료 알림
```

Camera.Core와 Movement.Core는 서로 참조하지 않는다. 조립 책임자인
PlayerRigController가 보기 결과의 yaw를 이동 계산에 전달한다.
Camera.Unity는 Movement.Unity를 참조하지 않고, PlayerRigController가 명시적으로 시점 결과를 전달한다.
Core는 Unity를 호출하지 않는다. 전역 Singleton이나 Event Bus를 두지 않는다.

## 4. 코드 작성 형태와 데이터 규칙

- public은 다른 담당자에게 공개할 계약만 사용한다. 내부 계산은 internal/private로 제한한다.
- Inspector 참조는 private 직렬화 필드로 보유하고 초기화 시 누락 여부를 검사한다.
- 설정은 공유 가능한 정의, 실행 상태는 캐릭터별 인스턴스다. 설정 에셋에 현재 속도·요청을 저장하지 않는다.
- 거리 m, 속도 m/s, 시간 초, 회전 각도 도를 사용한다. WorldPoint는 Unity 월드 축과 같은
  X=오른쪽, Y=위, Z=앞 좌표를 담되 Core에 UnityEngine.Vector3를 노출하지 않는다.
- float 비유한 값과 음수 시간·허용 범위 밖 설정은 경계에서 거절한다. 실패를 조용히 0으로 숨기지 않는다.
- Unity Vector3와 WorldPoint 변환은 Unity 계층의 경계에서 한 번 수행한다.
- 인터페이스는 엔진 교체·외부 호출·시험 대체가 필요한 경계에만 둔다.

### Core 코드 예시 — 보기 규칙

아래 코드는 책임 분리의 예다. 전체 파일 생성·컴파일 검증은 구현 단계에 진행한다.
이 예시는 입력 경계에서 비유한 값을 거절하고 감도를 검증했다는 전제다.

```csharp
namespace OpenSourceTeam6.Camera.Core
{
    public readonly struct LookState
    {
        public float YawDegrees { get; }
        public float PitchDegrees { get; }

        public LookState(float yawDegrees, float pitchDegrees)
        {
            YawDegrees = yawDegrees;
            PitchDegrees = pitchDegrees;
        }
    }

    public static class LookSolver
    {
        // delta는 이번 프레임의 마우스 이동량이다.
        public static LookState Step(
            LookState state, float deltaX, float deltaY,
            float degreesPerUnit, float minPitch, float maxPitch)
        {
            float yaw = (state.YawDegrees + deltaX * degreesPerUnit) % 360f;
            if (yaw < 0f) yaw += 360f;
            float pitch = state.PitchDegrees - deltaY * degreesPerUnit;
            pitch = System.Math.Max(minPitch, System.Math.Min(maxPitch, pitch));
            return new LookState(yaw, pitch);
        }
    }
}
```

LookSolver는 Unity 연결부에서 호출할 순수 계산 API로 공개한다.
입력 유효성 검사는 경계에서 수행하고, 계산 자체에는 장면 오브젝트를 넣지 않는다.

## 5. 외부 공개 API 계약

직원과 추후 일반 NPC는 각각의 인터페이스 인스턴스로 식별한다.
IAgentMovement의 Agent는 직원을 포함하는 이동 주체를 뜻한다.
이동 계약에는 직무·분노·구매·결제 같은 역할별 조건을 넣지 않는다.
외부 FSM에 NavMeshAgent나 내부 Transform을 노출하지 않는다.
아래는 시그니처 예시다. DTO의 구현은 별도 파일에서 작성한다.

```csharp
namespace OpenSourceTeam6.Movement.Core
{
    public interface IAgentMovement
    {
        MoveReceipt RequestMove(WorldPoint destination);
        bool Cancel(long requestId);
        MovementSnapshot Snapshot { get; }
        event System.Action<MoveOutcome> Finished;
    }

    public interface IPlayerInputGate
    {
        System.IDisposable AcquireLock(string reason);
        bool IsLocked { get; }
    }
}
```

| 자료형 | 내용과 규칙 |
|---|---|
| WorldPoint | 읽기 전용 X/Y/Z 좌표. 단위 m, 모든 값이 유한해야 함 |
| MoveReceipt | Accepted, RequestId, RejectReason. 거절 시 ID=0, 수락 시 ID>0 |
| MovementSnapshot | Position, ActualVelocity, State, ActiveRequestId, LastFailure. 값 복사로 제공 |
| MoveOutcome | RequestId, Status, Failure, Cancellation, FinalPosition. 실패·취소 사유를 구분하여 종료 결과만 제공 |
| MoveState | Idle / Planning / Moving / Suspended / Arrived / Failed / Cancelled |
| MoveFailure | None / InvalidDestination / NotReady / NoPath / PartialPath / PlanningTimeout / Stalled / DeadlineExceeded / TargetUnavailable |

- ID는 직원 인스턴스의 수명 안에서 증가한다. 새로 생성한 직원과 이전 직원의 ID를 혼용하지 않는다.
- 거절된 요청은 종료 알림을 보내지 않는다. 수락한 요청은 종료 결과를 한 번만 확정한다.
- Cancel은 현재 진행 중인 같은 ID만 취소한다. 이미 종료되거나 다른 ID면 false를 반환한다.
- 초기에는 외부 속도 변경 API를 제공하지 않는다. 성격 연동이 필요하면 Issue로 요청 범위를 합의한다.
- 요청·취소·조회·알림은 메인 스레드에서 처리한다. STT/LLM 결과가 백그라운드에서 도착하면
  호출자가 메인 스레드로 돌아온 뒤 직원의 유효성을 확인하고 요청한다.

### 알림 순서와 구독 수명

종료 상태 확정 → 경로 정리 → 결과 큐 저장 → LateUpdate에서 알림 순서로 처리한다.
RequestMove/Cancel 내부에서는 동기 알림을 보내지 않아 호출자가 ID를 저장하기 전에 알림이 오는 일을 막는다.

결과 큐와 프레임당 알림 상한은 직원당 64개로 시작한다. 큐가 차면 결과를 버리지 않고
새 요청을 NotReady로 거절한다. 기존 요청을 교체할 때는 취소 결과 저장 공간도 먼저 확인한다.
알림 중 구독 목록이 바뀌어도 이번 배포에는 목록의 스냅샷을 사용한다.
콜백에서 새로 생긴 결과는 다음 프레임에 배포하고, 한 구독자의 예외가 다른 알림을 막지 않도록 개별 기록한다.

OnDisable에서 신규 요청을 차단하고 진행 요청을 취소한 뒤 큐를 배포한다.
종료 처리 중 재요청도 거절하며 OnDestroy에서 같은 결과를 다시 보내지 않는다.
구독자는 자신의 OnDisable에서 구독을 해제하고 대기 상태를 정리한다.
이미 파괴된 구독자에게까지 배포를 보장하는 것은 아니다.

## 6. 플레이어 실행 흐름

담당 입력 에셋의 Gameplay 맵에 Move(Vector2/WASD), Look(Vector2/마우스 delta)를 둔다.
입력은 동적 업데이트 방식을 제안하며 기존 프로젝트 설정에 미치는 영향은 구현 시 확인한다.
PlayerInputReader가 매 프레임 한 번 읽고, Move 길이를 최대 1로 제한한다.
Look은 해당 프레임의 마우스 이동량이므로 deltaTime을 추가 곱하지 않는다.
게임패드의 각속도 입력은 별도 규칙이며 초기 범위에서 제외한다.

```text
PlayerRigController.Update
  1. 입력 잠금·포커스·일시정지 평가
  2. 입력 읽기: 잠금 중에는 Move/Look을 0으로 처리
  3. LookSolver로 yaw/pitch 계산
  4. yaw만 사용해 수평 이동 방향 계산
  5. MovementSolver로 수평 속도와 중력 속도 계산
  6. CharacterControllerMotor가 이동 차분을 한 번 적용
  7. 충돌 후 위치 차이 / dt로 실제 속도 기록
  8. 확정 상태를 CameraPresenter에 전달

FirstPersonCameraPresenter.LateUpdate
  확정 위치와 yaw/pitch를 눈 위치·카메라에 반영
```

CharacterController.Move는 중력을 자동 적용하지 않는다. 자체 수직 속도에 중력을 적분하고
수평·수직 이동 차분을 합쳐 한 번 이동한다. 바닥 접촉 시 하강 속도를 접지용 작은 값으로 되돌린다.
플레이어가 공중을 향해 보더라도 수평 이동에 pitch를 섞지 않는다.

입력 잠금은 조작만 막으므로 중력·충돌 처리는 계속한다. 게임 전체 일시정지는 별도이며,
dt=0이면 적분과 이동을 중단하고 실제 속도도 0으로 기록한다.
초기 이동 dt 상한은 0.05초다. 히치 시 실시간보다 이동 거리가 짧아지는 제한을 명시하고,
밀린 이동을 무제한 반복해 따라잡지 않는다. 일반 30/60/120FPS는 별도 비교한다.

본체 위치는 Motor, 본체 yaw는 PlayerRigController, 눈의 pitch는 CameraPresenter만 변경한다.
Rigidbody 이동·Animator Root Motion·직접 위치 가산을 동시에 적용하지 않는다.
입력·보기 계산은 O(1), 이동 요청은 캐릭터당 프레임에 한 번으로 제한한다.

### 중첩 잠금과 커서

AcquireLock은 개별 토큰을 반환한다. 토큰 해제는 여러 번 호출해도 한 번만 적용한다.
모든 토큰이 해제될 때까지 잠금을 유지해 UI 하나를 닫는 일이 다른 UI의 잠금을 풀지 않게 한다.
포커스 상실과 일시정지는 별도 토큰으로 관리한다.
잠금 중 커서를 표시·해제하고, 복귀 첫 프레임의 Look을 버려 시점 튐을 방지한다.
커서 상태 변경은 PlayerInputGate가 단독 담당한다.
입력 Action과 이벤트는 해당 컴포넌트가 소유한 것만 활성화·해제한다.

## 7. 눈 위치의 카메라와 자기 캐릭터 비표시

```text
PlayerRig                    위치·yaw·충돌 본체
├─ EyePivot                  눈 위치, pitch
│  └─ MainCamera             로컬 위치·회전은 원칙적으로 0
└─ LocalVisuals (후속 선택)   자기 몸 모델, 초기에는 배치하지 않음
```

- 초기 플레이어는 보이지 않는 충돌 형상이다. 검증용 캡슐의 Renderer를 남기지 않는다.
- 눈 위치는 임시로 발바닥에서 1.6m. 실제 캐릭터 비율을 적용할 때 사람의 눈 높이에 맞춘다.
- 모델을 추가하면 LocalVisuals의 Renderer를 명시적으로 비활성화하고 자기 그림자도 생성하지 않는다.
  이동·충돌까지 사라지지 않도록 PlayerRig 전체를 비활성화하지 않는다.
- 직원 모델과 환경은 정상적으로 표시한다. 자기 모델과 직원 모델의 표시 대상을 구분한다.
- 반사·추가 카메라가 도입되면 같은 비표시 요구를 다시 검증한다.
- 초기 충돌체 후보는 높이 1.8m, 반경 0.3m, 단위 스케일이다. 눈 위치는 충돌체 안에 둔다.
- near clip은 0.05m를 시작값으로 검증한다. 이 값을 낮추는 것만으로 벽 너머 보임을 해결하지 않는다.
- 플레이용 Camera와 AudioListener는 각각 하나만 활성화한다.

## 8. 직원의 경로 이동과 요청 관리

### 요청 처리

1. 활성화·NavMesh 위 배치·유한 좌표·설정·결과 큐 공간을 검사한다.
2. 허용 거리 내 목적지 보정이 가능한지 먼저 검사한다. 실패한 새 요청은 기존 이동을 취소하지 않는다.
3. 유효한 새 요청을 받아들이면 이전 요청은 Cancelled, 사유 Replaced로 종료한다.
4. 새 ID를 발급하고 Planning으로 전환한 뒤 목적지를 설정한다.
5. 경로 계산 대기 후 완전한 경로가 확인되면 Moving으로 전환한다.
6. 부분 경로·무효 경로·계산 시간 초과는 실패 결과로 돌려준다.

목적지는 NavMesh 위 최대 0.5m 투영을 초기값으로 사용하되 높이 차도 제한한다.
작업 위치는 선반 중심이 아니라 직원이 실제로 설 수 있는 바닥 위 좌표로 전달한다.
경로 설정 API가 성공했다는 사실은 도착 성공을 의미하지 않는다.

이전 경로를 정리하고 새 목적지를 설정한 뒤, 새 경로가 준비되기 전에 남은 거리로 도착을 판정하지 않는다.
요청 ID 확인만으로 엔진 내부의 오래된 경로 정보를 구별할 수는 없다.
새 요청 이후의 경로 대기·해결 상태를 확인하고, 동일 지점 요청은 별도 검증 분기로 처리한다.

### 종료 조건과 시간 제한 — 초기 검증값

| 조건 | 처리 |
|---|---|
| 완전 경로 + 유한 잔여거리 + 0.3m 이내 + 속도 0.05m/s 이하 | Arrived |
| 경로 계산 2초 초과 | PlanningTimeout |
| 3초간 유의한 진행 없음 | Stalled |
| 요청 전체 30초 초과 | DeadlineExceeded |
| 취소·요청 교체 | Cancelled |
| 대상 비활성화·NavMesh 이탈 등 | 원인에 맞는 실패 또는 취소 |

실패 사유와 취소 사유는 구분한다. CancelReason은 None / Requested / Replaced / Disabled로 정의한다.
MoveOutcome.Failure는 MoveFailure, Cancellation은 CancelReason을 반환한다.
도착 조건은 같은 지점 요청의 초기 상태에서도 시험한다.

초기 구현은 경계 오차를 고려해 잔여 거리에 0.01m, 실제 목적지 근접 거리에 0.05m 여유를 둔다.
이미 완전 경로를 확인했고 목적지에 도달한 뒤 Unity가 경로를 해제한 경우에는
유한한 실제 목적지 거리로 도착을 확인하고 이동을 정지한다. 새 요청의 미해결 경로에는 이 예외를 적용하지 않는다.

정체는 위치 이력과 경로 진행을 함께 관찰한다. 곡선 이동에서 목표와의 직선거리가 증가했다는
이유만으로 정체로 판정하지 않는다. 계속 회피하는 상황도 전체 제한 시간으로 종료한다.
초기 자동 재시도는 없으며 상위 FSM이 실패 결과로 다음 행동을 정한다.

일시정지는 Suspended로 전환해 이동과 게임시간 타이머를 멈추고 요청을 유지한다.
재개 시 경로가 유효한지 다시 확인하고 유효하지 않으면 실패 반환한다.
정지·경로 초기화 API는 활성·NavMesh 상태를 검사한 후 호출한다.
직원 위치·회전의 작성자는 NavMeshAgent 하나이며 Root Motion이나 별도 Motor로 덮어쓰지 않는다.

### 8.1 추후 일반 NPC 이동 확장

#### 캐릭터 종류별 책임

| 구분 | 이동 목적지를 정하는 기능 | 이동 기능의 책임 | 개발 범위 |
|---|---|---|---|
| 플레이어 | 키보드·마우스 입력 | 직접 보행·충돌·1인칭 시점 | 초기 구현 |
| 직원 | 음성 지시와 직원 행동 시스템 | 업무 위치로 이동, 요청 결과 반환 | 초기 구현 |
| 손님·방문자 | 추후 NPC 행동 시스템 | 지정 위치 간 이동, 대기·취소·실패 반환 | 후속 확장 |
| 주변 인물 | 추후 순찰·배회 규칙 | 경유 지점 이동과 정지 | 후속 검토 |

손님·순찰·배회는 사용 가능성을 설명하는 예시이며, 해당 콘텐츠의 개발 확정을 뜻하지 않는다.
직원에게만 허용된 업무 명령을 일반 NPC가 자동으로 받도록 만들지 않는다.
직원 대상 선택·역할 권한 검사는 호출 측이 수행하고 이동 계층은 요청 실행만 담당한다.

#### 재사용 구조와 파일 확장

직원 외 NPC를 도입할 때 EmployeeMovementController의 요청 수명·취소·결과 처리 부분을
공통 `AgentMovementController`로 분리한다. 기존 IAgentMovement 계약을 유지하면서
직원 프리팹의 기존 컴포넌트는 호환 어댑터로 남기거나 명시적인 마이그레이션을 수행한다.
직원과 손님용으로 이동 구현 전체를 복사하지 않으며, 공통화를 위해 역할별 FSM을 합치지도 않는다.

```text
외부 직원 행동 시스템 ─┐
                       ├→ IAgentMovement
추후 일반 NPC 행동 시스템┘     → AgentMovementController
                                ├→ MoveRequestTracker (개체별 상태)
                                └→ NavMeshAgentDriver

Movement/Unity/AgentMovementController.cs  공통 이동 실행·요청 관리
Movement/Unity/EmployeeMovementController.cs 기존 직원 연결 호환 경계
Movement/Unity/NpcMovementProfile.cs       후속 NPC 이동 설정이 필요할 때 추가
Prefabs/VisitorMovement.prefab            후속 일반 NPC용 프리팹
```

위 파일은 후속 확장 계획이며 지금 생성하지 않는다. 일반 NPC의 목적지 선택·순찰 순서·
구매/대기열 판단은 별도 소유자의 행동 모듈에 두고 이동 라이브러리에 포함하지 않는다.
별도 설정 타입은 실제 차이가 있을 때만 추가하며, 속도·반경 등 값만 다른 경우 기존 설정을 재사용한다.
공통화 과정에서 Unity 직렬화 참조와 .meta GUID를 보존하고 직원 씬·프리팹을 회귀 검증한다.

#### 일반 NPC의 움직임 예시

- 손님: 입구 → 지정된 상품 접근 위치 → 계산 대기 위치 → 출구.
  각 단계는 이전 이동의 Arrived를 받은 뒤 행동 시스템이 다음 요청을 보낸다.
- 주변 인물: 정해진 경유점 → 일정 시간 정지 → 다음 경유점.
  대기 시간과 다음 지점 선택은 이동 시스템 밖에서 관리한다.
- 어느 유형이든 Failed이면 행동 시스템에 결과를 반환한다.
  이동 시스템이 구매를 완료하거나 출구로 순간이동시키는 등 게임 결과를 임의 결정하지 않는다.

대기열 자리 예약과 작업 위치 점유는 경로 이동만으로 해결되지 않는다.
필요하면 별도 위치 예약 기능이 자리 토큰을 관리하고 행동 시스템이 획득·해제한다.
NavMesh 회피를 대기열 순서나 자리 독점의 보장으로 취급하지 않는다.

#### 생성·제거·혼합 이동

- 생성 시 이동 가능한 NavMesh 위치와 종류별 충돌 크기를 검증한다.
- 직원과 일반 NPC 모두 한 개체당 이동 실행자 하나만 위치를 쓴다.
- 제거·비활성화 시 진행 요청을 취소하고 구독을 해제한다.
  오브젝트 풀을 도입하면 재활성화 때 세션 식별자를 갱신해 이전 세션의 결과를 무효화한다.
- 요청 식별은 인스턴스와 요청 ID의 조합으로 처리하며 서로 다른 NPC의 같은 숫자 ID를 혼동하지 않는다.
- 혼잡한 통로에서는 회피·정체·시간 제한을 함께 검증한다.
  인원 증가를 이유로 매 프레임 전 개체의 경로를 다시 요청하지 않는다.
- 경로 요청의 분산·상한은 혼합 인원 측정 후 결정한다. 인원 제한과 생성 제어는
  상위 스폰/행동 시스템이 담당하며 이동 코드에서 임의로 NPC를 삭제하지 않는다.

### 8.2 일반 NPC 확장 검증 기준

후속 도입 시 다음 검증을 해당 Issue의 완료 기준으로 추가한다.

- 직원과 손님이 같은 공통 이동 계약으로 각각 독립된 목적지에 도착한다.
- 직원 대상 음성 명령이 손님에게 잘못 연결되지 않는다.
- 일반 NPC의 취소·실패·제거가 직원의 요청과 상태에 영향을 주지 않는다.
- 연속 경유점, 대기 중 취소, 출구 이동 실패를 행동 시스템이 구분할 수 있다.
- 공통화 전후 직원의 도착·취소·실패 API 동작이 유지된다.
- 개인 씬에서 혼합 이동 검증 후 공용 씬에 반영한다.
  전체 수뿐 아니라 직원/일반 NPC 구성 비율, 통로 혼잡도, 경로 요청량을 기록해 측정한다.

## 9. 다른 담당자의 사용 예시

다음은 계약 사용 예시이며 FSM 자체를 구현한 코드가 아니다. DTO 선언은 5장의 계약을 따른다.

```csharp
using OpenSourceTeam6.Movement.Core;

public sealed class MoveToWorkExample : System.IDisposable
{
    private readonly IAgentMovement movement;
    private long pendingId;

    public MoveToWorkExample(IAgentMovement movement)
    {
        this.movement = movement;
        movement.Finished += OnFinished;
    }

    public bool Begin(WorldPoint target)
    {
        MoveReceipt receipt = movement.RequestMove(target);
        if (!receipt.Accepted) return false;
        pendingId = receipt.RequestId;
        return true;
    }

    private void OnFinished(MoveOutcome result)
    {
        if (result.RequestId != pendingId) return;
        pendingId = 0;
        // 호출자가 결과 상태에 따라 업무·대기·실패로 전환한다.
    }

    public void Dispose()
    {
        movement.Finished -= OnFinished;
        if (pendingId != 0) movement.Cancel(pendingId);
        pendingId = 0;
    }
}
```

Unity 측 조립 컴포넌트가 인터페이스를 명시적으로 주입한다.
매 프레임 전체 씬 검색으로 직원을 찾지 않는다. 소유자가 비활성화되면 구독과 요청을 정리한다.
이승재는 이 계약으로 음성·FSM을 연결하고 내부 소스를 직접 변경하지 않는다.

각 씬에 조명, Camera, AudioListener를 준비한다. NavMesh도 씬별로 베이크·저장하며
개인 씬을 함께 열어야만 공용 씬이 작동하는 의존성을 만들지 않는다.

개인 씬 검증 → 프리팹·설정 반영 → 공용 씬 연결 → 공용 씬 단독 검증 →
PR 검토 → develop 통합 → 다른 담당자에게 공용 씬 편집 인계 순서다.
공용 씬은 안정된 HaJongUk/Prefabs 경로의 프리팹을 참조해도 되며 통합 때문에 복제·이동하지 않는다.
개인 실험용 오브젝트를 무조건 공용 씬에 복사하지 않는다.

공용 씬 편집 담당을 Issue에 기록하고 동시 편집을 피한다.
다른 담당자가 UI·스토리를 추가하는 것과 이동 내부 소스를 바꾸는 것은 별개다.
개인 작업 씬의 Git 제외 여부는 별도 결정이며 이 문서에서는 .gitignore를 수정하지 않는다.

## 11. 검증 계획과 완료 기준

### Core 테스트

- 대각선 입력 제한, yaw만 사용하는 수평 방향, 0초 시간, 잘못된 설정 거절.
- pitch 양끝 제한과 yaw 순환, 동일 입력의 동일 계산 결과.
- 중첩 잠금의 부분 해제와 중복 토큰 해제.
- 요청 교체·취소·오래된 결과 무시·종료 한 번 보장·큐 포화.
- 요청 타이머는 주입한 시간으로 검사하고 실제 대기 시간을 사용하지 않는다.

### Unity 연동·PC 빌드 검증

- 장애물 없는 직선 10초 이동을 30/60/120FPS에서 비교한다.
  3m/s에서 약 30m, 조건 간 차이 1% 이내를 목표로 한다. 히치 제한 발동은 별도 기록한다.
- 벽·지면 충돌, 눈 위치와 상하 한계, 자기 몸·그림자·반사 비표시를 검증한다.
- UI 잠금 중 중력, 게임 일시정지, 포커스 복귀 입력 튐을 구분해 검사한다.
- 직원의 정상·동일점·불가능·부분 경로·정체·대기·취소·파괴·연속 요청을 검사한다.
- 콜백 중 재요청·구독 변경·구독자 예외·종료 중 재요청을 검사한다.
- 개인·공용 씬을 각각 단독 실행하고, 공용 씬만으로 기능이 작동하는지 확인한다.
- Core의 엔진 참조 차단과 일반 PC 빌드의 Editor/Test 코드 제외를 확인한다.

### 성능 확인

직원 1명 합격 후 5명·10명을 측정점으로 사용하되 이를 최종 상한으로 확정하지 않는다.
정상 프레임의 자체 규칙·입력 계산은 정기 GC 할당 0B를 목표로 측정한다.
요청·알림 할당과 엔진 경로 탐색 비용은 별도로 기록한다.
장비·빌드·백엔드·해상도·인원·측정 시간·프레임 시간을 남겨 실제 상한 n을 정한다.
이 수치는 성능 달성 보장이 아니며 구현 후 측정해야 한다.

## 12. 구현 순서·변경·인계

| 단계 | 결과물 |
|---|---|
| 1 | 개인/공용 씬, 기본 프리팹, 폴더·어셈블리 경계 |
| 2 | Core 자료형·보기/이동 계산·잠금·요청 상태와 테스트 |
| 3 | 입력·플레이어 이동·눈 위치 카메라·자기 비표시 |
| 4 | 직원 1명 경로 이동·취소·실패·일시정지 |
| 5 | 공용 씬 연동·복수 직원·PC 빌드·사용 문서 |

일반 NPC 도입이 결정되면 별도 후속 단계로 공통 이동 실행자 분리, NPC 행동 모듈 연결,
혼합 이동 테스트, 직원 회귀 테스트를 진행한다. 이 확장은 위 초기 1~2주 작업의
필수 완료 조건에 자동으로 포함하지 않는다.

초기 예상은 약 1~2주이며 검증과 수정도 포함한다.
공개 API 변경 시 이승재와 영향 범위를 공유하고 호출 예시·테스트·변경 방법을 함께 수정한다.
이번 범위에 저장 데이터나 네트워크 상태 복제는 도입하지 않는다.

필수 참조 누락이나 불량 설정은 초기화 때 진단하고 해당 기능을 중단한다.
임의의 다른 오브젝트로 조용히 대체하지 않는다. 직원은 실패를 반환하고 플레이어는 조작을 중단한다.
검증된 프리팹·설정 변경 단위로 복원할 수 있게 하며 다른 담당자의 작업을 폐기하지 않는다.

인계 문서 앞부분에는 다음 정보를 둔다.
- 실행할 씬과 필수 환경·시작 방법
- 공개 API와 최소 사용 예시
- 완료 기능·미지원 범위·설정 변경 위치
- 실제 테스트 결과와 알려진 제약
- 공용 씬 편집 담당자와 수정 요청 방법
