# 카메라·캐릭터 이동 시스템 기획서

- 프로젝트: OpenSourceTeam-6 / 음성 지시 기반 AI 직원 편의점 운영 게임
- 담당: 하종욱
- 작성일: 2026-11-01
- 상태: 초기 시제품 구현 반영. 실행 방법·실제 공개 API·검증 결과는 [구현 및 인계 문서](카메라_캐릭터이동_구현및인계.md)를 참고한다.
- 확인 환경: Unity 6000.6.4f1, Input System 1.20.0, AI Navigation 2.0.14
- 대상: PC 키보드·마우스, 3D 싱글플레이 시제품

## 1. 목적과 검증할 경험

플레이어가 사장의 시점으로 매장 안을 이동하고 직원을 살펴볼 수 있는 기반을 만든다.
직원은 외부 시스템에서 지정한 목적지로 이동하고, 도착·중단·실패 결과를 반환한다.
음성 명령과 직원 행동 시스템을 나중에 연결해도 이동 내부를 수정할 필요가 없도록 한다.

첫 검증 장면은 “사장이 매장 안을 이동하며 직원에게 접근 → 테스트 명령으로 직원을
업무 위치로 이동 → 이동 결과 확인”이다. 음성·성격·감정·FSM은 이 단계의 구현 범위가 아니다.

## 2. 자체 라이브러리의 적용 방향

### 2.1 해결하려는 제약

입력 처리, 이동 규칙, 충돌 처리, 카메라 처리가 한 컴포넌트에 섞이면 수정 영향이 커진다.
프로젝트에 맞는 이동 규칙과 외부 명령 계약을 자체 코드로 관리하고,
엔진 연결부를 바꿀 수 있도록 분리하는 것이 목적이다.
특정 Unity 기능의 결함이나 성능 한계는 아직 재현·측정되지 않았으므로 단정하지 않는다.

### 2.2 Unity 활용 원칙

Unity 엔진 전체를 대체하지 않는다. 자체 라이브러리는 프로젝트에 맞는 규칙과
편집·확장 가능한 기능을 제공하며, 입력·물리·렌더링 등 필요한 엔진 기능은 Unity를 활용한다.
자체 구현 여부는 수정 필요성, 유지보수 비용, 검증 가능성, 개발 기간을 비교해 결정한다.
구체적으로 어떤 엔진 기능을 사용할지는 시스템 개발서에서 근거와 함께 정한다.

### 2.3 의존성 경계 — 제안

- Core: 순수 C#으로 이동 의도, 속도 규칙, 시점 각도 제한, 상태·명령·결과를 정의한다.
  UnityEngine / UnityEditor / Input System / Navigation 타입을 공개 계약에 노출하지 않는다.
  필요한 좌표·각도·시간 데이터의 표현은 개발서에서 결정한다.
- Unity: 입력, 실제 충돌·지면 판정, 경로 탐색, 장면 오브젝트 및 카메라 반영을 담당한다.
  Core가 요구하는 경계를 구현하고, 필요한 Unity 기능을 활용하되 선택한 연결 구현은
  게임 규칙과 분리해 수정할 수 있도록 한다.
- Editor: 설정 검사와 제작 도구만 담당한다. 플레이어 빌드의 런타임 의존성이 되지 않는다.
- Test: 규칙 단위 검증과 실제 엔진 연동 검증을 분리한다.

자체 namespace는 이름을 구분하는 수단이며 엔진 의존성을 제거하는 수단 자체는 아니다.
의존성은 코드 참조와 어셈블리 경계로 관리한다. namespace는
`OpenSourceTeam6.Camera.*`, `OpenSourceTeam6.Movement.*`를 제안한다.
`Unity.*`, `UnityEngine.*`, `UnityEditor.*`로 자체 코드를 명명하지 않는다.

소스와 .asmdef로 편집 가능한 라이브러리를 구성하는 방식을 우선 제안한다.
미리 컴파일한 DLL 배포는 별도 선택이며, 이번 기획 단계에서 DLL 파일을 만들지 않는다.
Core의 엔진 비의존성과 Unity 연결부의 엔진 활용을 구분한다.
입력·물리·렌더링을 포함한 엔진 전체 재구현은 이번 프로젝트 범위가 아니다.

## 3. 첫 개발 범위

| 구분 | 포함 | 제외·후속 검토 |
|---|---|---|
| 카메라 | 1인칭 시점, 좌우·상하 보기, 상하 각도 제한, 감도, 입력 잠금 | 3인칭, VR, 컷신, 헤드밥, 카메라 흔들림 |
| 플레이어 | 평면 보행, 정지, 중력·지면 유지, 벽 충돌, 대각선 속도 제한 | 달리기, 점프, 앉기, 계단·경사 고급 대응, 이동 플랫폼 |
| 직원 | 목적지 이동, 도착 판정, 취소, 실패 반환 | 업무 수행, 음성 해석, 감정 판단, FSM, 군중 시뮬레이션 |
| 연결 | 외부 호출 경계와 상태 조회, 테스트 명령 | 스토리·재화·엔딩 로직 |

계단과 경사는 우선 지원 범위를 제한한 평탄한 테스트 매장으로 검증한다.
직원 1명으로 시작하고 정상 동작 후 n명으로 확장한다. n의 상한은 통합 테스트에서 정한다.

## 4. 플레이 및 동작 규칙

### 4.1 1인칭 카메라

- 플레이어는 사람이며 카메라는 그 사람의 눈 역할을 한다. 캐릭터의 눈 위치에
  시점 기준점을 두고, 카메라는 이동과 자세에 맞춰 이 기준점을 따른다.
- 자신의 캐릭터는 플레이 화면에 보이지 않는다. 아래를 보거나 회전할 때도 머리·몸·손발이
  화면을 가리지 않도록 한다. 충돌·이동에 필요한 캐릭터 본체는 유지한다.
- 다른 직원과 환경은 정상적으로 보인다. 자기 캐릭터의 표시 제외 방식은 개발서에서
  정하며, 반사·그림자에 의한 자기 모습 노출도 검증하고 초기에는 제외한다.
- 마우스 좌우 입력은 플레이어의 수평 방향, 상하 입력은 시점의 수직 방향에 반영한다.
- 상하 각도는 설정 범위를 넘지 않으며 기본 시점에는 롤 회전을 적용하지 않는다.
- 이동 후 확정된 플레이어 위치를 기준으로 시점을 반영해 흔들림을 줄인다.
- 메뉴·대화 UI가 입력을 점유하거나 창 포커스를 잃으면 이동·시점 입력을 차단한다.
- 복귀 시 누적된 마우스 입력으로 갑자기 회전하지 않도록 이전 입력을 비운다.
- 커서 잠금·해제는 UI 담당자가 사용할 수 있는 연결 경계를 제공한다.

### 4.2 플레이어 이동

- WASD 입력을 시선의 수평 방향 기준으로 변환한다. 위를 보더라도 공중으로 이동하지 않는다.
- 대각선 입력이 직선 입력보다 빨라지지 않도록 입력 크기를 제한한다.
- 입력이 없으면 수평 이동을 정지한다. 초기에는 관성 없이 즉시 정지하는 방식을 제안한다.
- 바닥에는 서 있고 벽·진열대 등 충돌 대상은 통과하지 않는다.
- 충돌 해결 후 실제 위치·속도를 상태로 제공한다. 이동 의도와 실제 이동 결과를 구분한다.
- UI 잠금·일시정지·비활성화 중에는 입력이 남아 이동을 재개하지 않도록 한다.

### 4.3 직원 이동

- 행동 시스템이 “어디로 갈지” 결정하고, 이동 시스템은 “목적지까지 이동하고 결과를 알리는 일”만 수행한다.
- 대기 → 이동 중 → 도착 / 실패 / 취소의 결과를 구분한다.
- 새 요청은 기존 요청을 취소하고 교체한다. 요청 식별자로 이전 요청의 늦은 결과를 무시한다.
- 접근 불가능한 목적지, 경로 실패, 장시간 진행 없음은 실패 이유와 함께 반환한다.
- 도착 여부는 유효한 경로와 남은 이동 거리 등 실제 이동 상태로 판단하며,
  벽 반대편 목적지와 직선거리가 가깝다는 이유만으로 성공 처리하지 않는다.
- 실패 후 같은 이동을 무한 반복하지 않는다. 제한된 재시도·상위 재지시 정책은 개발서에서 정한다.
- 파괴·씬 종료·비활성화 시 진행 요청을 정리하며 결과는 한 요청당 한 번만 확정한다.

## 5. 조정 가능한 값 — 초기 테스트 제안

| 항목 | 제안값 또는 결정 방법 |
|---|---|
| 플레이어 보행 속도 | 3 m/s에서 매장 규모에 맞춰 조정 |
| 상하 보기 제한 | -80° ~ +80° |
| 카메라 높이 | 눈 위치를 기준으로 배치. 1.6 m는 임시값이며 캐릭터 비율에 맞춰 조정 |
| 직원 이동 속도 | 2 m/s에서 테스트 |
| 도착 허용 거리 | 0.3 m를 시작점으로 충돌체·업무 위치와 함께 검증 |
| 마우스 감도 | 입력 장치 단위와 변환 방식 확정 후 산정 |
| 정체 감지·시간 제한 | 테스트 경로 길이와 실제 속도 측정 후 개발서에 명시 |

공유 설정은 기본값이고 실행 중 상태는 캐릭터마다 별도로 보유한다.
동일 설정을 공유하는 직원끼리 위치·진행 상태를 공유하지 않는다.

## 6. 시스템 흐름과 소유권

플레이어: 입력 → 이동·보기 의도 → Core 규칙 → Unity 이동·충돌 적용
→ 실제 상태 확정 → 카메라 반영

직원: 외부 목적지 요청 → 요청 검증 → 경로·이동 처리
→ 상태 갱신 → 도착·취소·실패 결과 → 행동 시스템의 다음 판단

- 플레이어 위치의 작성자는 이동 연결부 하나로 제한한다.
- 직원 위치는 선택한 이동 구현 하나가 작성한다. 다른 시스템이 동시에 위치를 직접 덮어쓰지 않는다.
- 카메라 회전·입력 잠금의 적용 책임도 하나로 제한한다.
- 게임 오브젝트 변경은 엔진이 허용하는 메인 스레드에서 수행한다.
- 입력/이동/카메라 갱신 시점과 물리 동기화 방법은 이동 구현을 결정한 뒤 개발서에서 확정한다.
- 캐릭터별 상태는 생성부터 종료까지 소유하고 종료 시 요청·구독을 해제한다.
- Core는 명시적인 입력·시간·설정을 받아 계산한다. Unity 물리·경로까지 플랫폼 간
  완전 결정적이라고 보장하지 않는다.

## 7. 폴더·어셈블리 구상

담당 경로: `Assets/_Project/HaJongUk/`

```text
HaJongUk/
├─ Scripts/
│  ├─ Camera/
│  │  ├─ Core/       시점 규칙·상태·공개 계약
│  │  ├─ Unity/      입력·카메라 적용
│  │  ├─ Editor/     설정 검증 도구
│  │  └─ Test/       규칙 및 연동 테스트
│  └─ Movement/
│     ├─ Core/       이동 규칙·명령·결과·공개 계약
│     ├─ Unity/      플레이어·직원 이동 연결
│     ├─ Editor/     설정 검증 도구
│     └─ Test/       규칙 및 연동 테스트
├─ Scenes/          개인 작업·검증 씬
│  └─ HJU_CameraMovement_Work.unity
├─ Prefabs/         플레이어·직원 검증 프리팹
└─ Assets/          테스트용 설정·표현 자료
```

참조 방향은 Unity → Core, Editor → 필요한 Core/Unity,
Test → 검증 대상이다. Core → Unity, Runtime → Editor 역참조는 허용하지 않는다.
카메라와 이동 사이에는 필요한 읽기 전용 상태만 전달하고 순환 참조를 만들지 않는다.
실제 어셈블리 개수·파일명·테스트 플랫폼 분리는 개발서에서 확정한다.

WhiteOut 확인 결과: `D:/Unity/Projects/WhiteOut/MiniSurvival`에서
`Assets/01_Scenes`, `02_Scripts.meta`, `03_Prefabs.meta` 등의 구성은 확인했다.
그러나 실제 `02_Scripts`와 카메라·이동 소스·asmdef는 확인되지 않았다.
위 구조는 회의안을 반영한 임시 제안이며 WhiteOut 구현을 복제하거나 검증했다는 뜻이 아니다.

### 7.1 개발 시작 시 씬 분리

개발을 시작하는 첫 단계에서 다음 두 씬을 만든다. 현재는 생성 계획만 기록하며,
기획서 수정 단계에서 실제 씬 파일을 만들지는 않는다.

| 용도 | 예정 경로 | 운영 방식 |
|---|---|---|
| 개인 작업·검증 | `Assets/_Project/HaJongUk/Scenes/HJU_CameraMovement_Work.unity` | 하종욱이 기능 구현·실험·실패 상황을 검증하는 작업 씬 |
| 공용 통합·인계 | `Assets/_Project/Shared/Scenes/Team_Integration.unity` | 검증된 기능을 연결하고 develop 통합 후 다른 개발자가 이어서 작업할 씬 |

- 두 씬은 독립된 씬 파일과 고유한 .meta를 가진다. 기존 씬이 있으면 덮어쓰지 않고 확인한다.
- 개인 씬에서 검증한 기능은 재사용 가능한 프리팹·설정 중심으로 공용 씬에 반영한다.
  실험용 오브젝트·임시 디버그 기능을 공용 씬에 무조건 복사하지 않는다.
- 공용 씬에는 기본 카메라·조명·플레이어 시작 위치·직원 테스트 위치·충돌 가능한 바닥을
  준비한다. 실제 플레이 카메라는 하나만 활성화해 중복 시점을 방지한다.
- 공용 씬 자체로 카메라와 이동을 실행할 수 있어야 하며, 개인 씬을 함께 열어야만
  동작하는 참조나 개인 PC의 절대 경로에 의존하지 않는다.
- PR 검토와 공용 씬 연동 검증 후 develop에 반영한다. 씬 경로, 시작 방법,
  필수 프리팹·설정, 현재 편집 담당자를 인계 문서와 Issue에 남긴다.
- 통합 이후 공용 씬의 편집 담당자를 조율해 다른 개발자에게 인계한다.
  같은 씬을 동시에 수정하지 않으며, 공용 씬 편집 권한 인계가 하종욱의
  카메라·이동 내부 구현을 직접 수정할 권한을 의미하지는 않는다.

개인 작업 씬은 개인용 개발 공간이라는 뜻이다. Git에서 제외할지는 별도 결정이며,
기획서에서는 자동 제외하거나 .gitignore를 변경하지 않는다.

## 8. 다른 담당자가 이용할 기능 — 계약 초안

정확한 C# 시그니처·자료형은 시스템 개발서에서 정한다.

| 기능 | 입력 | 출력·주의점 |
|---|---|---|
| 플레이어 입력 잠금 | 잠금 요청/해제 | UI와 중첩될 때 한 요청의 해제가 다른 잠금을 풀지 않도록 설계 |
| 직원 목적지 요청 | 직원 대상, 목적지 | 요청 식별자, 수락 여부·거절 이유 |
| 직원 이동 취소 | 해당 요청 식별자 | 취소 결과; 이미 끝난 요청에 중복 효과 없음 |
| 이동 상태 조회 | 캐릭터 대상 | 위치, 실제 속도, 이동 상태·실패 이유의 읽기 전용 스냅샷 |
| 이동 종료 알림 | 요청 구독 | 도착/실패/취소 중 하나; 구독 수명·해제 책임을 명시 |

이승재는 공개 계약을 통해 명령하고 결과를 받아 FSM을 진행한다.
성격에 따른 이동 속도 변경이 필요하면 범위가 검증된 설정 경계로 요청한다.
송재명은 UI 입력 잠금과 상태 표시 경계를 사용한다.
하종욱 담당 내부 구현을 직접 수정하거나 Transform을 외부에서 덮어쓰지 않는다.
기능 추가·계약 변경은 Issue로 요청하고 연동 검토 후 반영한다.

## 9. 완료 기준과 검증 장면

| 검증 | 기대 결과 |
|---|---|
| 보행·대각선 이동 | 같은 시간에 대각선만 더 멀리 이동하지 않음 |
| 시점 조작 | 제한 각도 준수, 이동 방향에 시점 상하 기울기가 섞이지 않음 |
| 눈 위치·자기 모습 | 눈 높이에서 시야 제공, 아래 보기·회전·벽 접근 시 자기 몸이 보이지 않고 직원·환경은 정상 표시 |
| 벽·바닥 | 매장 경계 통과 및 바닥 아래 추락 없이 이동 |
| UI·포커스·복귀 | 이동·회전 중단, 복귀 순간 입력 튐 없음 |
| 직원 유효 목적지 | 이동 후 도착 상태와 완료 알림을 한 번 전달 |
| 도달 불가·정체 | 정해진 제한 안에 실패 반환, 게임 전체가 멈추지 않음 |
| 요청 교체·취소 | 이전 요청 결과가 새 요청을 완료시키지 않음 |
| 다중 직원 | 개별 상태와 결과가 섞이지 않음 |
| 씬 재시작·종료 | 남은 요청·구독·이전 입력으로 다음 실행이 오염되지 않음 |
| 구조 검증 | Core에 Unity 참조 없음, Editor 코드가 플레이어 빌드에 포함되지 않음 |
| 씬 분리·인계 | 개인·공용 씬이 독립적으로 열리며 공용 씬만으로 실행 가능, 다른 개발자가 인계 절차로 작업 재개 가능 |

Core 검증, Unity 연동 검증, PC 플레이어 빌드 확인을 구분해 기록한다.
30/60/120 FPS 조건에서 이동 거리와 조작 차이를 비교한다. 허용 오차와 기준 장비는 개발서에서 정한다.
한 직원 검증 후 n명 확장 시 프레임 시간·할당·이동 요청 처리 지연을 측정한다.
성능 향상은 측정 전 보장하지 않으며 모든 직원의 경로 재계산을 매 프레임 강제하지 않는다.

## 10. 개발 단계와 인계

1. 기획 검토: 자체 규칙과 Unity 활용 경계, 최소 조작, 평탄한 매장 범위, WhiteOut 원본 확인.
2. 개발서 작성: 이동 구현 후보 비교, 자료형·공개 API·어셈블리·갱신 순서·시간 제한 확정.
3. 개발 시작 시 개인 작업 씬과 공용 통합 씬을 먼저 생성하고 독립 실행 기반 준비.
4. 플레이어 이동과 눈 위치의 1인칭 카메라를 개인 작업 씬에서 연결.
5. 직원 한 명의 목적지 요청·취소·실패 처리 구현.
6. 검증된 기능을 공용 씬에 연결해 통합 검증과 n명 확장 가능성 확인 후 사용 문서 작성.
7. 요청된 협업 절차에 따라 PR 검토 및 develop 통합 후 공용 씬과 공개 계약을 인계.

범위는 약 1~2주를 목표로 개발서에서 산정하며, 일정 안에는 검증과 수정도 포함한다.
인계 문서는 기능 목록, 공개 API, 연결 예시, 주의 사항, 확인한 테스트,
남은 제약을 앞부분에 배치한다. 실제 커밋·PR·push는 별도 요청 시 진행한다.

## 11. 남은 결정과 위험 대응

- Unity 활용 범위: 엔진 전체를 대체하지 않는 원칙 아래, 기능별 자체 구현·엔진 활용 경계를 개발서에서 확정.
- 이동 구현: 자체 규칙 아래 실제 충돌·경로 탐색을 어떤 구현으로 연결할지 개발서에서 비교.
- WhiteOut: 의도한 소스가 다른 경로에 있다면 해당 원본을 확인한 뒤 구조를 조정.
- 일정 확대: 물리 엔진 전체 재구현은 제외하고 경로 탐색도 기존 기능 활용 가능성을 먼저 검토.
- 카메라 떨림·중복 이동: 위치 작성자와 갱신 순서를 통일하고 연동 장면으로 검증.
- 고정 수치와 맵 불일치: 속도·도착 거리·충돌 크기를 같은 테스트 장면에서 조정.
