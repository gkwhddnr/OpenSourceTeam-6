# 손님·행인 NPC 행동 트리 시스템 개발서

담당: 하종욱 | 상태: 전용 테스트 씬에서 기본 동작 검증 | 갱신: 2026-11-19

## 전용 테스트 씬

Unity에서 `Assets/_Project/HaJongUk/Scenes/HJU_CustomerNpc_Test.unity`를 열고 Play를 누른다. 이승재의 `VoiceIntegrationTest` 씬을 참고해 27×27m 편의점, 진열대, 계산대와 출입구 앞 보도를 구성했다. 테스트 씬 전용 NavMesh와 프리팹을 사용한다.

- 빨간 캡슐은 진열대에서 테스트 상품을 집은 뒤 계산대에서 순서대로 계산하고 외부 목표로 이동한다. 파란 캡슐은 보도를 지나간다.
- 두 역할 모두 보도 왼쪽 또는 오른쪽 영역에서 무작위로 생성된다. 출현 지점과 반대편 도착 지점은 영역 안의 NavMesh에서 개체마다 뽑는다. 손님은 계산 후 출입구를 거쳐 도착 지점으로 가고, 행인은 보도를 건넌다.
- 왼쪽 패널에서 역할별 `-` 및 `+`로 동시 유지할 목표 인원을 조절한다. 숫자는 현재 인원과 목표 인원이다. 인원 증가는 생성 간격에 따라 순차 적용된다. `Checkout queue`에서 손님별 순서와 대기 경과 초를 볼 수 있다.
- `Prev day`와 `Next day`는 테스트 일차를 바꾼다. 컨트롤러의 인스펙터에서 일차별 손님·행인 기본값을 설정할 수 있다. 테스트 기본값은 1일차 2/2, 2일차 3/4, 3일차 4/6이다. 별도 설정이 없는 일차는 앞선 설정을 이어받는다. 본편 일차 연동 시 동일한 `SetDay` 진입점을 사용할 수 있다.

씬의 계산은 대기열 확인용 모의 처리다. 실제 재고·결제·오디오·영업 마감 연동은 아래 본편 계약을 따른다. 테스트 UI의 일차 전환은 인원 설정만 적용한다.

## 자료 충돌과 연동 기준

2026-11-07 팀 공유 마스터의 직원 외 NPC 보류 계획과 충돌하는 범위는 이후 회의 결정을 따른다. **11월 30일 중간발표 목표는 손님이 입장해 상품을 집고 계산한 뒤 퇴장하며 하루가 마무리되는 루틴**이다. 이 중 손님 동선과 대기열을 전용 테스트 씬에서 검증했다. 독촉·대기 시간 초과 이탈·인지도·평가 감소는 추후 확장으로 둔다. 직원 감정과 혼잡 연동 규격은 [Issue #13](https://github.com/gkwhddnr/OpenSourceTeam-6/issues/13)을 따른다.

현재 로컬 UI는 `RecordWorkSample` 기반 매출과 `StoreUiSessionController`의 시간 종료 시 정산 호출을 사용한다. 손님 거래 기반 매출을 연결할 때 기존 가상 매출과 중복 합산하지 않도록 경제·UI 소유자와 기준을 결정한다. 종료 시점에 손님 정리 후 정산할지, 즉시 정산할지는 기존 UI와 합의 전이며 조기 마감 또한 마스터 문서상의 제안이다. 이 문서는 정산 함수를 추가로 호출하거나 조기 마감이 구현되었다고 가정하지 않는다.

## 범위와 우선순위

11월 30일 중간발표용 최소 흐름은 손님 1명의 입장 → 상품 집기 → 계산대 이동·결제 확인 → 출구 통과 → 매장 밖 목표 도착이다. 도시 보도를 지나는 행인 역할도 설계하되 시연 포함 여부와 구현 시기는 협의한다. 실제 재고·결제·영업 마감 연결은 상대 시스템의 API와 정책 확인이 선행된다. 1인 시연에서는 연동 전 임시 어댑터를 사용할 수 있으나 실제 매출·재고 반영 완료로 표시하지 않는다. 소란은 도입 검토 중이며, 실제 상품 탐색과 위치 질문은 추후 확장이다. 손님과 행인에게 감정·페르소나·직원 업무 지시 판단을 구현하지 않는다.

## 역할별 경로 설계

스폰 담당자는 제안된 역할 `Customer` 또는 `Pedestrian`과 시작 지점·목표를 지정한다. 역할을 결정한 뒤 각자의 트리와 컨텍스트를 만들며, 한 실행 중 임의 전환하지 않는다. 역할 전환과 확률·간격·최대 인원은 합의 전 설정 미정이다. NPC별 이동 실행자와 요청 ID는 독립적으로 관리한다.

```text
손님: 외부 출현 → 입구 → 상품 → 계산 → 출구 → 외부 목표 → 정리
행인: 보도 출현 → 보도 경유점(선택) → 외부 목표 → 정리
```

행인 경로는 입구·구매·결제 노드를 실행하지 않으며 손님 수·계산 대기열·혼잡 이벤트에 등록하지 않는다. 손님은 실제 입장 확정 시에만 입장 이벤트를 보낸다. 경로점과 스폰·제거 범위는 최종 맵 및 NavMesh 확정 후 배치한다. 행인이 입구를 우연히 지나도 역할만으로 입장 처리하지 않는다.

행인 이동 실패 시 유한 재시도 후 정리하고, 씬 종료·풀 반환 시 이동 취소와 구독·실행 세대를 초기화한다. 일시정지 시 손님·행인의 이동과 트리를 함께 멈춘다. 영업 종료는 신규 손님 유입을 중단하지만 행인 생성·유지 여부는 별도 합의한다.

## 제안 트리와 노드 계약

```text
우선순위 Selector (매 평가마다 마감·취소부터 확인)
├─ Sequence [마감/취소 감지 → 진행 작업 중단·자원 반환 → 퇴장 → 외부 목표 이동]
└─ Sequence [입장 → 상품 선택 → 진열대 이동 → 집기 결과 확인
             → 계산대/대기 위치 이동 → 결제 결과 확인 → 퇴장 → 외부 목표 이동]
```

각 이동·집기·결제 노드는 요청 후 실제 결과까지 `Running`, 성공 확인 시 `Success`, 실패 시 `Failure`를 반환한다. 구매 분기의 실패는 취소 정리와 퇴장으로 연결한다. 우선순위 Selector는 구매 중에도 마감 조건을 재평가하고 활성 자식을 중단해야 한다. 구체적인 노드 구현과 재시도 횟수는 제안이며 구현 전 조정한다. 대기 시간 초과 이탈·독촉·소란·질문은 현재 트리에 포함하지 않는다.

## 계산대 대기 계약 (우선 구현 제안)

계산대 단위 FIFO 대기열이 순서와 자리 예약을 소유한다. 손님은 대기열 합류 확정 시 각각 대기 시작 시간을 기록하며 앞사람의 계산 중에도 자신의 시간이 흐른다. 앞사람의 처리 완료 또는 이탈 시 다음 손님이 앞으로 이동하고, 계산 처리자는 동시에 한 손님만 소유한다. 여러 계산대의 수와 선택 정책은 맵·경제 담당자와 협의한다.

```text
대기열 합류 → 손님별 경과 시간 측정·표시 → 순서에 따라 계산 시작
                                             → 대기 종료 → 결제 결과 대기
```

합류부터 계산 시작 직전까지 활성 시뮬레이션 시간으로 경과 시간을 누적하고, 일시정지 중 누적하지 않는다. 첫 손님이 결제 처리를 시작했는지는 타이머나 도착 추정이 아니라 결제 담당자의 승인 이벤트로 확인한다. 계산대 소유자가 순서와 처리 시작을 메인 스레드에서 직렬화한다. 결제 실패 및 영업 마감 중 처리는 별도 합의한다. 시간 경과만으로 자동 독촉하거나 이탈하지 않는다.

손님별 스냅샷은 식별자·대기열 순번·경과 시간·대기 상태를 UI 어댑터에 전달한다. 시간값은 내부에서 정확히 유지하되 표시 갱신 주기와 포맷은 UI 담당자와 정한다. UI 미연결이나 출력 실패가 대기열을 중단시키지 않게 한다.

**추후 확장:** 기본 대기 한도 초과 시 소리 또는 대사 독촉, 추가 한도 초과 시 구매 전체 취소·예약 반환·퇴장, 이탈에 따른 인지도·평가 감소를 검토한다. 한도·수치·UI/오디오·평가 API와 취소 확인 정책은 관련 담당자와 합의한다. 이 기능들은 현재 구현 또는 완료 기준에 포함하지 않는다.

전용 씬에서 한 계산대에 여러 손님이 합류했을 때 순서와 독립적인 대기 시간을 확인했다. 본편 연동 시 결제 승인/실패, 대기열 반환, UI 미연결을 추가 확인한다. 독촉과 시간 초과 이탈의 경계·중복 이벤트·평가 연동 테스트는 해당 기능 구현 시 추가한다.

## 구조와 실행

전용 씬의 `NpcPopulationController`는 출현 인원과 역할별 행동 순서를 제어한다. `NpcNavigation`은 보도 영역 표본 추출과 개체별 NavMesh 이동을 담당한다. `NpcCheckoutQueue`는 대기 순서, 계산대 점유, 대기 시간과 모의 계산 시간을 관리한다. 두 클래스는 컨트롤러 내부에서 사용하므로 씬에 연결할 컴포넌트는 기존과 같다. 아래 이동 인터페이스와 외부 계약은 본편 연동 설계다.
`OpenSourceTeam6.Customers.Core`에 Selector, 실행 위치를 기억하는 Sequence, Condition, 비동기 Action을 둔다. 노드는 Success/Failure/Running을 반환한다. 각 NPC는 별도 트리 인스턴스와 컨텍스트를 소유한다. `.Unity`의 대표 컨트롤러가 이동·재고·결제·대기열 어댑터를 주입한다.

루트는 마감·취소 정리 분기를 우선 확인하고 구매 Sequence를 실행한다. 이동 Action은 요청을 한 번 전송한 후 결과를 기다린다. 매 프레임 새 이동 요청을 보내지 않는다. 완료·실패·취소·중단 시 Action의 자원을 해제한다.

## 이동 연결
기존 `OpenSourceTeam6.Movement.Core.IAgentMovement`의 `RequestMove(WorldPoint)`, `Cancel(requestId)`, `Snapshot`, `Finished`를 사용한다. 요청 수락은 도착 성공을 뜻하지 않는다. Finished의 RequestId와 현재 실행 세대를 비교하여 교체되거나 취소된 요청의 결과를 무시한다. 이동 코어의 경로·회전·NavMesh 내부 상태는 외부에서 직접 변경하지 않는다.

## 외부 계약
상품 선택·예약·획득, 계산 대기열 예약·반환, 결제 요청·성공 확인은 실제 담당 코드 확인 후 어댑터 계약을 확정한다. 재고 감소와 금액 반영은 해당 시스템의 책임이다. NPC는 결과를 확인하고 다음 행동으로 전환한다. 거래 ID로 중복 처리를 막고 NPC 삭제·마감 등 명시적인 취소 시 예약을 반환한다. 대기 시간 초과로 인한 취소는 추후 확장이다.

본편 연동 제안: 재고 소유자는 선택 상품의 판매 가능 여부와 품절 결과를 반환한다. 품절 시 다른 선택 또는 구매 취소 정책은 합의한다. 결제 소유자는 거래 ID·상품 목록·처리 주체(직원/플레이어)·승인 및 확정 결과를 제공하고, 경제·직원 소유자는 매출·직원 건수 수당과 계산 주체에 따른 영향의 적용 여부와 시점을 결정한다. 손님 트리는 결과를 기다리고 흐름을 전환할 뿐 수당·직원 감정이나 실제 금액을 직접 변경하지 않는다. 수당·직접 계산 페널티·일차별 이벤트는 마스터의 후보이며 이번 우선 구현 보장 범위가 아니다.

### 추후 확장: 진열 구역 탐색과 질문

상품 및 매장 배치가 늘어나면 손님은 목표 상품의 좌표를 처음부터 넘겨받지 않고, 방문한 진열 구역에서 발견한 상품 정보에 따라 다음 구역 탐색 또는 상품 접근을 결정하도록 설계한다. 현재 테스트의 임의 지점 경유 후 지정 상품으로 이동하는 방식은 실제 탐색 구현이 아니다. 접근 불가 구역과 탐색 종료 조건은 맵·상품 담당자와 협의한다.

찾지 못한 경우 손님은 직원 또는 플레이어에게 이동해 상품 위치를 질문한다. 요청에는 질문자·대상·상품·요청 ID를 포함하고, 대상 선택, 대사 UI, 응답·안내와 취소의 계약은 담당 시스템과 협의한다. 답변으로 위치를 알게 된 경우 그 위치를 탐색에 반영한다. 무응답과 품절을 구분하며 재시도 및 대체·퇴장 정책은 미정이다. 직원의 감정 판단과 업무 선택을 NPC 트리에서 구현하지 않는다.

확장 구현 시 여러 진열 구역에서 목표를 찾는 경우, 찾지 못해 직원과 플레이어에게 각각 질문하는 경우, 안내 후 이동, 품절·무응답·접근 불가 및 NPC 제거 시 요청 정리를 검증한다.

## 정지와 실패 처리
공통 일시정지 신호에서 트리와 실제 이동을 함께 정지한다. 이동의 기존 중단·재개 계약을 구현 전에 확인하며 일시정지를 취소·재요청으로 대체하지 않는다. 경로 실패·재고 부족은 유한 재시도 후 퇴장하도록 설계한다. 계산 대기 시간 초과에 따른 자동 퇴장은 추후 확장이다. 풀 반환 시 이벤트 구독·실행 세대·예약·현재 행동을 초기화한다.

## 구현 순서와 검증 계획
시간 코어 이후 단일 손님의 입장·진열대 이동, 상품 획득, 계산대·결제, 퇴장·외부 목표 이동, 마감 취소를 순서대로 연결한다. 행인은 공통 이동 계약을 사용하되 별도 역할의 보도 경로를 구현한다. 다수 NPC와 행인 시연 범위는 팀 일정에 따라 확장한다.

본편 연동 시에는 도착과 획득의 구분, 결제 중복, 이동 실패, 늦은 콜백, 마감 중 거래, 일시정지, NPC 삭제·풀 재사용을 전체 하루 루틴에서 확인한다. 전용 테스트 씬에서는 두 역할별 동선, 모의 계산, 손님별 대기 기록과 일시정지, 인원 API와 일차 프리셋을 Unity Play Mode에서 확인했다.

통합 씬에서는 `NavMeshSurface`가 유효한 베이크 데이터를 보유하고 입구·진열대·계산대·출구·외부 목표 및 에이전트 시작 위치가 연결된 이동 가능 영역에 있는지 확인한다. 현재 `HJU_Time_UI_Integration` 씬의 Surface에는 데이터가 없어 베이크·연결이 선행되어야 한다. Play에서 실제 `NavMeshAgent` 생성과 전 구간 이동을 확인한다. 이 확인은 시간·UI 연동 성공 여부와 별개다.

행인 검증 시에는 보도 시작점·경유점·종점의 NavMesh 연결과 건물·도로 장애물을 확인한다. 손님과 행인이 동시에 움직일 때 서로의 요청·정리에 영향을 주지 않는지, 행인이 입장·결제 이벤트와 혼잡 집계를 발생시키지 않는지, 실패·일시정지·풀 재사용이 정상 처리되는지 확인한다. 동시 인원과 성능 목표는 맵 규모 및 대상 기기 측정 후 정한다.


## Issue #13 효과음·혼잡 연동 계약
이슈에서 지정한 호출은 입장 확정 시 `audioPlayer.PlaySfx(StoreSfxId.StoreDoorChime)`, 결제 확정 시 `audioPlayer.PlaySfx(StoreSfxId.BarcodeCheckout)`이다. 이번 로컬 검색에서는 해당 효과음 식별자와 최신 지속 스트레스 API를 확인하지 못했다. 이슈의 연동 규격으로 기록하고 최신 UI/오디오 코드 병합 후 이름·어셈블리·접근성을 확인한다. 동일 이름의 대체 구현을 임의로 추가하지 않는다.

입장 이벤트는 NPC 실행 세대별로, 결제 이벤트는 거래 ID별로 한 번만 발행한다. NPC는 오디오 어댑터로 알림만 보내며 결제·입장 효과를 오디오 재생 성공 여부에 의존시키지 않는다. 실패·재시도·오래된 콜백에서 효과음이 중복 재생되지 않게 한다.

매장 범위의 혼잡 집계자가 실제 계산 대기 인원과 활성 소란 원인을 관리한다. 손님마다 전체 직원 스트레스를 갱신하지 않는다. 제안 스냅샷은 대기 인원·혼잡 여부·소란 여부·세대이며, 직원 상태 소유자에게 `isStoreCrowdedOrNoisy = crowded || noisy`를 전달한다. 혼잡 임계값과 해제 임계값은 설정으로 두고 경계에서 반복 전환되지 않도록 한다. 소란은 원인별 핸들을 등록·해제하고 NPC 제거·씬 종료 시 누락 없이 반환한다.

직원 소유자는 `StressRules.EvaluateContinuousStressDelta`의 실제 시그니처를 확인한 후 활성 시뮬레이션 경과 시간과 역할·페르소나를 사용해 지속 증감을 한 곳에서 적용한다. 일시정지·정산 중에는 누적하지 않는다. 명령 즉발 스트레스·시급 조정·행동 확률 계산은 기존 직원/UI 규칙에 맡긴다. 다음 날 시작 시 혼잡과 소란 런타임 상태를 초기화한다.

추가 검증: 다중 손님의 혼잡 중복 가산 방지, 혼잡과 소란 동시 발생, 한 원인만 종료된 상태, 대기열 이탈·풀 반환, 일시정지 중 스트레스 정지, 거래 재시도 시 결제음 중복 방지. 최신 규칙 병합 전에는 이슈 규격과 로컬 구현의 차이를 해결한 것으로 보고하지 않는다.
